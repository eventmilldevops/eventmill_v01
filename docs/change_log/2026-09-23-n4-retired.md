# 2026-09-23 — Stage N4 retired, unbuilt

**Decision, with a small code change to match. Suite unchanged at 1844.**
Decision 12 in `docs/specs/attack_path_detection_normalization.md`.

## What N4 was

The last normalization stage. It would add a `normalize_paths` action that
saved the context pack as its own artifact
(`detection_context_pack_<ts>_<run_id>.json`), a pack schema, a
`metadata.kind` of `attack_path_detection_context_pack`, and a
`generate_detections` route that took a pack id instead of the exports. Its
gate: the pack round-trips, and re-normalizing is byte-identical apart from run
id and timestamp.

## Why it is no longer needed

Each thing N4 was for is already done another way.

| N4 was for | What does it now |
|---|---|
| Reviewing the fixtures with no provider and no cost | `validate_input` (the full pack) and `digest` (09-20, the readable form) |
| The pack as a registered artifact, with `show` and `export` | The shell auto-persists any successful result that registers nothing, as `json_events` (established in N1, decision 8) |
| Re-examining a bad draft against the exact pack it saw | Normalization is deterministic, so re-deriving gives the same pack |
| `generate_detections` taking a stored pack | No consumer. Normalizing is free, and a stored pack would be a second editable copy able to drift from the exports. Analyst edits belong in the flow map (decision 9) |

The third row is the one that could have been wrong, so it was **tested before
the decision, not assumed.** Each of the four fixture pairs (`022646`,
`122549`, `123525`, `124121`) was normalized twice with its flow map, and the
JSON was compared with sorted keys. All four were identical, at 146,388,
181,655, 175,117 and 204,662 characters. The pack has no timestamp or run id of
its own. That is a stronger result than N4's gate asked for.

## What is still owed, and where it went

Re-deriving a pack means knowing which inputs a run used. A generation result
records `engagement.run_id`, the export's `flow_map_sha256`, `prompt_version`
and `telemetry_library_version`. **It does not record the supplied flow map's
own hash or lineage, or the designer's code identity.** With an edited map
supplied, the export's hash names the map that was projected, not the one that
enriched the nodes. The designer plan (§8 step 8) already puts "input and
optional-context hashes" in the workbook's JSON sidecar, so this moves to
**G1d**. It does not justify reviving N4.

**Revive N4 if** something has to consume a pack without the exports, such as
a catalogue import or a second tool. A schema and `metadata.kind` are only worth
having once something reads them.
